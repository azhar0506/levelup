### Kubernetes API

- Primary Interface where Users and System components interact with Kubernetes cluster.
- A RESTful API that provides operations to create, read, update and delete resources such as pods, services, volumes, etc.
- Users interact using tools like:
    - kubectl
    - helm
    - client libraries
- Monitoring tools:
    - Metric Server
    - Prometheus

Kubernetes componenets also use the API:
- kube-scheduler uses the API to watch Pods/Nodes and assign Pods to Nodes
- kubelet uses the API to report node/pod status and receive instructions on what to run
- controllers (controller manager) use the API in control loops to maintain desired state
- Admission Controllers enforce policies and optionally modify requests before they are persisted:
    - enforce quotas and limits
    - set defaults
    - validate configurations
    - accept or reject requests based on cluster state


### Kubernetes API request lifecycle (high level)

1.	Request arrives
Client sends an HTTPS request (typically on port 6443).
	
2.	Route matching
API server routes the request based on URL and HTTP method (GET, POST, PUT, DELETE).
	
3.	Authentication
Verifies identity (tokens, API keys, certificates).
Invalid → request rejected.

4.	Authorization
Checks permissions using the configured --authorization-mode
(e.g. RBAC, Node, Webhook).
Fails → request denied.
	
5.	Admission control
Admission Controllers accept, reject, or mutate the request based on policies.
	
6.	Validation
Ensures request data is correctly formatted and valid.
	
7.	Request handling
Resource is created/updated/deleted (often persisted in etcd).
	
8.	Response generation & sending
API server returns HTTP status and response body.

### Custom Resource Definitions (CRDs)

- CRDs extend the Kubernetes API by adding new resource types.
- Custom resources behave like native ones (Pods, Services, Deployments).
- Enables platforms like Database-as-a-Service via Kubernetes.
- Resources can be applied, updated, deleted with kubectl, while implementation details are handled behind the scenes.

### API Versioning

### Alpha
Name looks like: v1alpha1.

Default: Disabled; must be explicitly enabled on the API server.

Stability: High risk - may contain bugs; APIs can change or be removed without notice.

Support/Longevity: No guarantees; not recommended beyond short-lived testing clusters.

### Beta
Name looks like: v2beta3.

Default: Disabled (except for betas introduced before v1.22, which were enabled by default).

Stability: Well tested and generally considered safe to enable/use

Migration: Incompatible changes may occur; upgrades may require edits/re-creation (possibly downtime).

Support/Longevity: Typical window: up to ~9 months or 3 minor releases to deprecation, then another similar window to removal.

Production use: Not recommended due to potential breaking changes.

### Stable (GA)
Name looks like: vX (e.g. v1), potentially prefixed with a category apps/v1

Default: Enabled; widely supported.

Stability: Backwards-compatible within a Kubernetes major version.

Support/Longevity: Remains available for all future releases within a major version (there are no current plans for a major version that removes stable APIs)

Let's create a pod via the API

```sh
curl --location 'http://localhost:8001/api/v1/namespaces/default/pods?pretty=true' \
--header 'Content-Type: application/json' \
--header 'Accept: application/json' \
--data '{
    "kind": "Pod",
    "apiVersion": "v1",
    "metadata": {
        "name": "nginx",
        "creationTimestamp": null,
        "labels": {
            "run": "nginx"
        }
    },
    "spec": {
        "containers": [
            {
                "name": "nginx",
                "image": "nginx",
                "resources": {}
            }
        ],
        "restartPolicy": "Always",
        "dnsPolicy": "ClusterFirst"
    },
    "status": {}
}'
```

If we check, we can now see our pod that was created via the API

```sh
kubectl get pods
```

Output:

```sh
NAME    READY   STATUS    RESTARTS   AGE
nginx   1/1     Running   0          75s
```

We will also delete a pod, via the api, again the process for generating this is outlined in the video

```sh
curl --location --request DELETE 'http://localhost:8001/api/v1/namespaces/default/pods/nginx' \
--header 'Content-Type: application/json' \
--header 'Accept: application/json' \
--data '{
    "gracePeriodSeconds": 1,
    "propagationPolicy": "Background"
}'
```

And if we check our pods again, this will no longer exist

```sh
kubectl get pods
```

Output:

```sh
No resources found in default namespace.
```
