# Service_Meshes

### Purpose of a Service Mesh

A Service Mesh is used to manage service-to-service communication in a microservices architecture.

It helps with:
•	Reliable communication
•	Security between services
•	Observability (metrics, tracing)
•	Traffic control

### Why Service Meshes Exist

Microservices introduce complexity:
•	Many services
•	Many network calls
•	Harder security and visibility

A service mesh:
•	Handles this outside the application code
•	Adds functionality without rewriting services

### Core Components of a Service Mesh

Data Plane

•	Handles actual network traffic
•	Implemented using proxies
•	Responsible for:
	•	Traffic routing
	•	Encryption (mTLS)
	•	Retries, rate limiting, circuit breaking
	•	Telemetry collection

Proxy (Sidecar)

•	A proxy runs alongside each service
•	Intercepts inbound and outbound traffic
•	Provides fine-grained traffic control

Control Plane

•	Manages and configures the proxies
•	Does not handle application traffic
•	Acts as the central management layer


## Service Mesh Architectures

•	Sidecar proxy model
	•	Proxy per service
	•	Most common approach
•	Node-level proxy model
	•	Proxy per node
	•	Simpler, fewer features


## Key Features You Should Recognise

Service meshes commonly provide:
•	Mutual TLS (mTLS)
 → Two-way authentication between services
•	Traffic management
•	Observability
•	Reliability mechanisms


## Common Open Source Service Meshes

•	Istio
•	Linkerd
•	Traefik Mesh


## Service Mesh Interface (SMI)

Service Mesh Interface (SMI):
•	A standard API specification
•	Designed to work across different service meshes
•	Prevents vendor lock-in
•	Defines common capabilities such as:
	•	Traffic management
	•	Access control
	•	Metrics
