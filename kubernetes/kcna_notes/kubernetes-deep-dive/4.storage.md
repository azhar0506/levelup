# Kubernetes Storage

## What is Ephemeral Storage

Ephemeral storage is temporary storage that exists only for the lifetime of a Pod.
It does not survive Pod restarts or deletion and is automatically removed when the Pod is terminated.
	•	Used for temporary data, caches, or scratch space
	•	Very fast when memory-backed
	•	Example:
	•	emptyDir volume
	•	Can be disk-backed or memory-backed
	•	emptyDir.medium: Memory creates a RAM-based filesystem
	•	Ideal for caches or temporary files

Once the Pod is deleted, the data is lost.

## What is Persistent Storage

Persistent storage is storage that outlives Pods.
Data remains available even if a Pod is deleted and recreated.

In Kubernetes, persistent storage is managed through:
	1.	StorageClass – defines how storage is provisioned
	2.	PersistentVolume (PV) – the actual storage resource
	3.	PersistentVolumeClaim (PVC) – a request for storage by a Pod

Pods mount storage via PVCs, not directly via PVs.

At the time of the video, Kubernetes-native storage options were limited.
One major CNCF-aligned solution highlighted is:

## What is Rook

Rook is a Kubernetes storage operator that:
	•	Runs distributed storage systems inside Kubernetes
	•	Automates deployment, scaling, healing, and management
	•	Abstracts complex storage operations behind Kubernetes APIs

Rook itself is not a storage system — it is an orchestrator.


## What is Ceph
Ceph is a distributed storage system
Provides:
•	Object storage
•	Block storage
•	File storage
•	Highly scalable, fault-tolerant, and production-grade
•	Commonly used in enterprise and cloud environments


## Relationship Between Rook and Ceph
•	Ceph = the storage engine
•	Rook = the Kubernetes operator that manages Ceph

👉Rook is designed to ease the orchestration of Ceph in Kubernetes


Rook:
	Deploys Ceph inside Kubernetes
	Manages Ceph clusters using CRDs
	Handles upgrades, failures, and scaling automatically

Think of it as:

Ceph does storage — Rook makes Ceph Kubernetes-friendly


### Reclaim Policies (Very Exam-Important)

Reclaim policies define what happens to storage when a PVC is deleted:
Delete:
•	Underlying storage is deleted
•	Default for dynamically provisioned volumes
Retain:
•	Storage remains after PVC deletion
•	Requires manual cleanup
•	Common for manually created PVs
Recycle (largely deprecated):
•	Performs a basic scrub of data

### Manual vs Dynamic Provisioning

Manual provisioning:
•	Admin creates PV first
•	PVC binds explicitly
•	Usually uses Retain
	•	Dynamic provisioning:
•	PVC automatically creates PV via StorageClass
•	Default reclaim policy is Delete

## Persistent Storage

Let's take a look at the storageclasses available in our cluster, we will have a single storageclass and it will be marked as default

```sh
kubectl get storageclass
```

Output

```sh
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  10m
```

We'll create a persistent volume using the k3s storageClass of local-path

```sh
cat <<EOF > manual_pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: manual-pv001
spec:
  storageClassName: local-path
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: "/var/lib/rancher/k3s/storage/manual-pv001"
    type: DirectoryOrCreate
EOF
```

And we will apply this file

```sh
kubectl apply -f manual_pv.yaml
```

Output:

```sh
persistentvolume/manual-pv001 created
```

Check the available persistent volumes and note that the reclaim policy is set to Retain

```sh
kubectl get pv
```

Output

```sh
NAME           CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
manual-pv001   10Gi       RWO            Retain           Available           local-path     <unset>                          36s
```

Let's now create a manual persistent volume claim against this persistent volume

```sh
cat <<EOF > manual_pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: manual-claim
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
  resources:
    requests:
      storage: 10Gi
  storageClassName: local-path
  volumeName: manual-pv001
EOF
```

Apply this file:

```sh
kubectl apply -f manual_pvc.yaml
```

And check the persistent volume claim:

```sh
kubectl get persistentvolumeclaim

# OR

kubectl get pvc
```

Output:

```sh
NAME           STATUS   VOLUME         CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
manual-claim   Bound    manual-pv001   10Gi       RWO            local-path     <unset>                 14s
```

## Dynamic PVC

Let's create a dynamic version of our Persistent Volume Claim, this will be similar to our manual approach but without a volumeName entry -

```sh
cat <<EOF > dynamic_pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dynamic-claim
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
  resources:
    requests:
      storage: 10Gi
  storageClassName: local-path
EOF
```

Let's apply this

```sh
kubectl apply -f dynamic_pvc.yaml
```


```sh

    run: ubuntu
  name: ubuntu
spec:
  nodeSelector:
    kubernetes.io/hostname: worker-1
  containers:
  - command:
    - sleep
    - infinity
    image: ubuntu
    name: ubuntu
    resources: {}
    volumeMounts:
    - mountPath: /manual
      name: manual-volume
    - mountPath: /dynamic
      name: dynamic-volume
  dnsPolicy: ClusterFirst
  restartPolicy: Always
  volumes:
    - name: manual-volume
      persistentVolumeClaim:
        claimName: manual-claim
    - name: dynamic-volume
      persistentVolumeClaim:
        claimName: dynamic-claim
status: {}
EOF
```
