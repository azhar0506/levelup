# statefulSets

## What is StatefulSet

A StatefulSet is a Kubernetes workload API object used to manage stateful applications.

Unlike Deployments, StatefulSets are designed for workloads that:
	•	Need stable identities
	•	Need dedicated persistent storage per Pod
	•	Require ordered startup, shutdown, and updates

Typical examples include databases, message brokers, and clustered services.

## Purpose of StatefulSets

StatefulSets are used when an application requires:
	•	Stable, unique Pod names
	•	Stable network identities
	•	Stable, persistent storage per Pod
	•	Ordered and predictable scaling and updates

Each Pod in a StatefulSet is not interchangeable.


## StatefulSets vs Deployments (Differences & Similarities)

Similarities
	•	Both manage multiple Pods
	•	Both support scaling
	•	Both support rolling updates
	•	Pod templates (spec) are very similar

Differences

 Feature           | Deployment                     | StatefulSet                          |
|-------------------|--------------------------------|--------------------------------------|
| Pod identity      | Randomised                     | Stable & predictable                 |
| Pod names         | Random suffix                  | `<name>-0`, `<name>-1`, `<name>-2`   |
| Storage           | Shared PVC (if used)           | One PVC per Pod                      |
| Pod replacement   | New Pod, new identity          | Same identity restored               |
| Ordering          | No guarantee                   | Ordered create/update/delete         |
| ReplicaSets       | Uses ReplicaSets               | No ReplicaSets                      |

Deployments are typically stateless
StatefulSets are explicitly stateful

## Why Persistent Storage Works Differently

	•	In a Deployment, all Pods share the same volume
	•	In a StatefulSet, each Pod gets its own PVC

Example:

	•	3 Pods → 3 PVCs → 3 PVs
	•	Storage is uniquely tied to each Pod identity

Even if a Pod is deleted, its storage remains and is reattached when the Pod is recreated.

## Pod Identity & Naming

StatefulSet Pods use predictable names:

```sh
<statefulset-name>-0
<statefulset-name>-1
<statefulset-name>-2
```

	•	The ordinal index starts at 0
	•	Pod names do not change, even if the Pod is rescheduled
	•	IPs may change, but DNS names stay consistent

This is critical for clustered systems that depend on peer identity.


## Dependency on Services for Naming

StatefulSets depend on Services—specifically Headless Services—for stable DNS.

Headless Service
	•	clusterIP: None
	•	No load balancing
	•	Exposes individual Pod endpoints directly
	•	Required for stable Pod DNS

DNS Format

```sh
<pod-name>.<service-name>.<namespace>.svc.cluster.local
```

Example:

```sh
nginx-1.nginx.default.svc.cluster.local
```

Without a Service, StatefulSets cannot provide stable network identities.

## Ordered Deployment & Scaling

StatefulSets guarantee ordering:
	•	Pods are created one at a time
	•	Scaling up/down happens in order
	•	Deletion happens in reverse order

This behaviour is essential for systems like databases that require controlled startup/shutdown.

## Rolling Updates & Partitioning

StatefulSets support partitioned rolling updates.
	•	updateStrategy.rollingUpdate.partition
	•	Only Pods with an ordinal ≥ partition value are updated

Example:
	•	Partition = 2
	•	Only pod-2 and above are updated
	•	pod-0 and pod-1 remain unchanged

This enables:
	•	Canary deployments
	•	Phased rollouts
	•	Safer upgrades for stateful systems


## Persistent Storage Behaviour

- PVCs are created using volumeClaimTemplates
- One PVC per Pod
- Storage persists even if:
	- Pod is deleted
	- StatefulSet is deleted

If the StatefulSet is recreated:
	- Existing PVCs are reused
	- Data is preserved
	- Identity and state are restored

This is a core guarantee of StatefulSets.

# Lab

There isn't a quick way of creating a StatefulSet from the CLI but a Deployment gets us very close, we'll mock up a Deployment and tee to a file

```sh
kubectl create deployment nginx --image=nginx --replicas=3 --dry-run=client -o yaml | tee statefulset.yaml
```

And we'll modify this, to change it to a StatefulSet, we're also going to include a reference to serviceName

```sh
cat <<EOF > statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  creationTimestamp: null
  labels:
    app: nginx
  name: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  serviceName: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - image: nginx
        name: nginx
EOF
```

And let's apply this file:

```sh
kubectl apply -f statefulset.yaml
```

## Stateful Persistent Storage

Update our statefulset to include a dynamic volume

```sh
cat <<EOF > statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  labels:
    app: nginx
  name: nginx
spec:
  selector:
    matchLabels:
      app: nginx
  serviceName: nginx
  replicas: 3
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - image: nginx
        name: nginx
        volumeMounts:
        - name: nginx
          mountPath: /data
  volumeClaimTemplates:
  - metadata:
      name: nginx
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "local-path"
      resources:
        requests:
          storage: 1Gi
EOF
```
