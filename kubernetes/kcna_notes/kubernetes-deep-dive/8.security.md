# Kubernetes Security

## Security Contexts

SecurityContexts control what a Pod or container is allowed to do
•	They define things like:
	•	Running as non-root
	•	User and group IDs
	•	Preventing privilege escalation
•	They apply at Pod / container level, not cluster-wide

## Admission Controllers

•	Admission Controllers are gatekeepers for the Kubernetes API
•	They can allow, modify, or reject requests before resources are created
•	Used to enforce security and policy rules cluster-wide


## Legacy: Pod Security Policies (PSPs)

•	Pod Security Policies used to enforce security rules
•	They applied at cluster and namespace level
•	They are deprecated and removed (1.25+)


## Security Tools (Awareness Only)

Falco
•	Runtime security monitoring
•	Detects suspicious behaviour in containers
Open Policy Agent (OPA / Gatekeeper)
•	Policy enforcement via Admission Controllers
Kubescape
•	Scans clusters for vulnerabilities & misconfigurations
•	Supports NSA and CISA hardening standards


## OpenID Connect (OIDC)

OIDC = authentication
•	Built on OAuth 2.0
•	Allows Kubernetes to use external identity providers
•	Kubernetes verifies users via JWT tokens
•	Used before RBAC authorization


## The 4C’s of Cloud Native Security 

	1.	Cloud
	2.	Cluster
	3.	Container
	4.	Code

Key idea:
	•	Security is layered
	•	Each layer protects the one inside it



# Lab

Let's start with Security Contexts which define privilege and access control settings for a Pod or Container. We will use a custom image that includes a rogue binary for demonstration purposes. This binary allows escalation from a normal user to root in a Kubernetes pod

```sh
kubectl run ubuntu --image=spurin/rootshell:latest -o yaml --dry-run=client -- sleep infinity | tee ubuntu_secure.yaml
```

Output:

```sh
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: ubuntu
  name: ubuntu
spec:
  containers:
  - args:
    - sleep
    - infinity
    image: spurin/rootshell:latest
    name: ubuntu
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}
```

Let's apply this to create the pod in our Kubernetes cluster

```sh
kubectl apply -f ubuntu_secure.yaml
```

Output:

```sh
pod/ubuntu created
```

With the pod running, let's execute into it and observe the current user privileges. You'll notice that we have root access

```sh
kubectl exec -it ubuntu -- bash
```

Output:

```sh
root@ubuntu:/# 
```

Let's exit out of the pod

```sh
exit
```

Modify our YAML file to include a Security Context that specifies running as a non-root user with a specific UID and GID

```sh
cat <<EOF > ubuntu_secure.yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: ubuntu
  name: ubuntu
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
  containers:
  - args:
    - sleep
    - infinity
    image: spurin/rootshell:latest
    name: ubuntu
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}
EOF
```

Let's replace the existing pod with our updated configuration. This replacement might take a little longer

```sh
kubectl replace --force -f ubuntu_secure.yaml
```


Output:

```sh
pod "ubuntu" deleted
pod/ubuntu replaced
```

Let's exec into the pod again. This time, you'll observe that we're logged in as a non-root use


```sh
kubectl exec -it ubuntu -- bash
```

Output:

```sh
nonpriv@ubuntu:/$ 
```

If we run id, this will confirm we are a non root user

```sh
id
```

Output:

```sh
gid=1000(nonpriv) groups=1000(nonpriv)
```

However, if we run the /rootshell binary this will allow privilege escalation

```sh
/rootshell
```

Output:

```sh
/rootshell
root@ubuntu:/# 
```


Repeat this command until we exit the container

```sh
exit
```

To further secure our pod, we will add an additional Security Context to the container specification, disallowing privilege escalation

```sh
cat <<EOF > ubuntu_secure.yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: ubuntu
  name: ubuntu
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
  containers:
  - args:
    - sleep
    - infinity
    image: spurin/rootshell:latest
    name: ubuntu
    resources: {}
    securityContext:
      allowPrivilegeEscalation: false
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}
EOF
```


Again, let's replace the pod with our new security settings

```sh
kubectl replace --force -f ubuntu_secure.yaml
```

Output:

```sh
pod "ubuntu" deleted
pod/ubuntu replaced
```

Now, exec into the pod one more time:

```sh
kubectl exec -it ubuntu -- bash
```

And try to escalate privileges, you can try this multiple times, the command will succeed but without root priviledge

```sh
/rootshell
```

Output:

```sh
root@ubuntu:/# 
```


```sh
id
```

Output:

```sh
uid=0(root) gid=1000(nonpriv) groups=1000(nonpriv)
```

And issue exit until we fully exit the container

```sh
exit
```

Finally, let's clean up by deleting the pod and removing the YAML file -

```sh
kubectl delete -f ubuntu_secure.yaml --now ; rm -rf ubuntu_secure.yaml
```
