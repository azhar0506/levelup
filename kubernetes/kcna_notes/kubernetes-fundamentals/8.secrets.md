# Secrets

- Object for storing sensitive information
- Used for Passwords, Tokens and Key - or anything else sensitively
- You don't need to store confidential information in your application

## What a TLS Secret is (and why it exists)

A TLS Secret is a Kubernetes Secret with a well known type: `kubernetes.io/tls`. 

It exists as a standard convention so common Kubernetes components (especially Ingress / Gateway controllers) know exactly where to find the certificate and private key without extra configuration.

A TLS secret normally containers:

- `tls.crt` -> the server certificate (PEM-encoded)
- `tls.key` -> the private key (PEM-encoded)
- (optional) `ca.crt` -> a CA bundle for some user-cases (client auth / mTLS chains)

### The user of Kubernetes TLS Secrets in the Cloud Native Ecosystem?

TLS secrets are also a common formated used by other CLoud Native applicatoins:
- Certmanager makes use of Kubernetes secrets as its output format
    - allowing ease of consumption from the likes of Ingress and Gateway API

## Labs

Create a secret using the --from-literal approach which is identical in usage to that of ConfigMaps, send the output to yaml as a dry-run and note the encoded values for COLOUR and KEY

```sh
kubectl create secret generic colour-secret --from-literal=COLOUR=red --from-literal=KEY=value --dry-run=client -o yaml
```

Output:

```sh
apiVersion: v1
data:
  COLOUR: cmVk
  KEY: dmFsdWU=
kind: Secret
metadata:
  creationTimestamp: null
  name: colour-secret
```

We can verify that this is a base64 encoded value by passing the same value and encoding it ourselves with base64 manually

```sh
echo -n value | base64
```

Output:

```sh
dmFsdWU=
```

And we can also decode this by reversing the base64 encoding

```sh
echo dmFsdWU= | base64 -d
```

Output:

```sh
value
```

Let's run our previous example and create the secret

```sh
kubectl create secret generic colour-secret --from-literal=COLOUR=red --from-literal=KEY=value
```

Output:

```sh
secret/colour-secret created
```

List available secrets

```sh
kubectl get secrets
```

Output:

```sh
NAME            TYPE     DATA   AGE
colour-secret   Opaque   2      6m19s
```

And show the yaml output for the secret, we will see the encoded secrets within 

```sh
kubectl get secret/colour-secret -o yaml
```

Output:

```sh
apiVersion: v1
data:
  COLOUR: cmVk
  KEY: dmFsdWU=
kind: Secret
metadata:
  creationTimestamp: "2026-01-22T09:05:11Z"
  name: colour-secret
  namespace: default
  resourceVersion: "2853"
  uid: d675cf51-d595-434d-8c29-657b268998f4
type: Opaque
```

We'll re-use our ubuntu pod that sleeps for infinity and dumps environment variables, this time we will use envFrom with secretRef, the following is a complete yaml example

```sh
cat <<EOF > env-dump-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: ubuntu
  name: ubuntu
spec:
  containers:
  - command:
    - bash
    - -c
    - env; sleep infinity
    image: ubuntu
    name: ubuntu
    resources: {}
    envFrom:
    - secretRef:
        name: colour-secret
  dnsPolicy: ClusterFirst
  restartPolicy: Never
status: {}
EOF
```

We'll apply this and create our ubuntu pod

```sh
kubectl apply -f env-dump-pod.yaml
```

Output:

```sh
pod/ubuntu created
```

If we view the logs for this, we can see our secrets listed accordingly in a similar way to the use of ConfigMaps 

```sh
kubectl logs ubuntu
```
